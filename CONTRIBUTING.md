# Contributing to K_and_S

Thank you for using K_and_S! This document explains how to contribute your porting
learnings back to the bundle so other GPU porters can benefit from your work.

## Quick Start

1. Use the K_and_S MCP server during your porting work:
   - `read kands://porting-strategies` — decide Copy vs Adapt vs Rewrite
   - `read kands://porting-patterns` — find CUDA↔HIP↔Vulkan↔DirectX patterns
   - `record_performance` — track your measured performance
   - `suggest_optimizations` — get suggestions from your perf history
   - `estimate_performance` — compare to theoretical estimates

2. When you discover something new, contribute it back:

```bash
export_contribution(engine_name="my-gpu-engine", arch="gfx1201", workload="flash_attn")
```

This generates a template in `findings/my-gpu-engine.md`.

3. Edit the template with your findings, then submit a PR:
   ```bash
   git add findings/my-gpu-engine.md
   git commit -m "docs: add porting report for my-gpu-engine on gfx1201"
   git push origin main
   gh pr create --title "Porting report: my-gpu-engine → gfx1201"
   ```

## What to Contribute

### 1. Porting Reports (`findings/`)

Create a new file in `findings/` for each porting project you complete. Use the template generated by `export_contribution`.

Name convention: `findings/<engine-name>.md` (e.g., `findings/llama-cpp-vulkan.md`)

Required sections:
- **Summary** — one paragraph on what you ported
- **Performance History** — table of measured tok/s over time
- **Key Learnings** — what worked, what didn't
- **Architecture Notes** — arch-specific quirks you discovered
- **Porting Patterns Used** — Copy/Adapt/Rewrite decisions
- **Verification** — checkbox list (CPU oracle parity, numerical stability, etc.)

### 2. Architecture Updates (`ARCH_MAP.json`)

If you port to a new GPU that's not in `ARCH_MAP.json`, add it:

```json
"gfx1201": {
  "name": "RDNA4 (RX 9070 XT)",
  "vendor": "AMD",
  "vendor_id": "gfx1201",
  "wave_size": 32,
  "lds_kib": 128,
  "tensor_cores": false,
  "wmma": false,
  "dot4": true,
  "dot8": true,
  "bf16_native": true,
  "fp8_native": false,
  "known_issues": ["no rocWMMA; Vulkan CM broken — use DP4a"],
  "isa_docs": "https://gpuopen.com/machine-readable-isa/",
  "isa_disassembler": "IsaDecoder API (https://github.com/GPUOpen-Tools/isa_spec_manager)"
}
```

### 3. Porting Patterns (`PORTING_PATTERNS.json`)

If you discover a new transformation pattern (e.g., "CUDA warp shuffle → Vulkan subgroup"), add it:

```json
"cuda_to_vulkan": {
  "warp_shuffle": {
    "cuda": "__shfl_down_sync(0xffffffff, val, offset)",
    "vulkan": "subgroupShuffleDownINTEL(val, offset)",
    "notes": "Requires GL_KHR_vulkan_glsl. Use subgroupOps in SPIR-V."
  }
}
```

### 4. Performance Benchmarks (`PERF_BENCHMARKS.json`)

Add your real-world measurements alongside the theoretical estimates:

```json
"workload_estimates": {
  "flash_attn_4096": "3.2 ms/token (measured on RX 9070 XT with EXL3-4bit)"
}
```

### 5. Toolchain Entries (`TK_TOOLS.json`)

If you use a new compiler, SDK, or toolchain config, add it:

```json
"vulkan": {
  "name": "Vulkan Compute",
  "compiler": {"glslc": "${VULKAN_SDK}/bin/glslc.exe"},
  "cooperative_matrix": {
    "amd": "BROKEN — use DP4a fallback",
    "nvidia": "Supported via GL_NV_cooperative_matrix"
  }
}
```

### 6. Reference Links (`ISA_REFERENCES.md`)

If you find new machine-readable ISA docs, add them. The bundle's value is
being the single source of truth — every vendor doc you find, we can all use.

## Contribution Checklist

Before submitting a PR:

- [ ] Your porting report is engine-agnostic (uses generic terms, not engine-specific names)
- [ ] You've recorded actual measured performance via `record_performance`
- [ ] You've verified correctness against a CPU oracle
- [ ] You've noted any arch-specific gotchas in `known_issues`
- [ ] You've checked that your addition doesn't duplicate existing entries
- [ ] You've updated the relevant JSON schema if adding new fields
- [ ] **No placeholder/stub code** — every kernel must produce real output
- [ ] **No "fake it works" hacks** — fallbacks must be correct, not stubs

## Code Style

- JSON files use 2-space indentation
- Markdown uses `##` headers for sections, `|` tables for data
- Tool descriptions are ≤120 chars on first line
- Resource URIs follow the `kands://` namespace convention
- Python files use `from __future__ import annotations` + type hints
